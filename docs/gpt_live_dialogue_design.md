# GPT Live級の対話体験に向けた設計書

## 1. 目的と到達基準

目的は、単に音声を文字にして応答することではなく、相手が話し始めた瞬間から状況を理解し、自然な間・相槌・割り込み・感情・継続話題を扱える常時接続の対話体験を作ることである。

本書でいう「GPT Live級」は、特定サービスの内部実装を再現する意味ではない。次の利用者体験を達成する目標である。

- 相手の短い相槌では話を止めず、意味のある割り込みでは自然に減衰して止まる。
- 相手の話が終わる見込みを推定し、早すぎず遅すぎないタイミングで返答を始める。
- 最初の音声応答を、発話終了から通常1秒以内、許容上限1.5秒で開始する。
- 直前の話題、再生中の音楽、画面、相手の感情、ペルソナ状態を会話状態として一貫して扱う。
- 不確かな事実、未解析の音源、聞き取れなかった発話を知ったふりで補完しない。

## 2. 現状と不足している要素

現行実装には、VAD、faster-whisper、文単位TTS、割り込み判定、Style Manager、ペルソナ別のMind、DeepSearch、音楽の再生状態共有がある。これは有効な基礎である。

一方で、Live体験の中核となる以下はまだ独立した層として不足している。

- 発話途中の音声・テキストから意図と発話終端を予測するリアルタイム理解。
- 音声の聞き取り、感情、会話行為、割り込み判定を統合するターン管理。
- 低遅延の音声入出力を一つのセッションで扱う全二重オーケストレータ。
- 応答生成を「考える内容」「どう話すか」「いつ話すか」に分離する制御面。
- 音楽・動画・画面・ツール結果を会話中の世界状態として扱うコンテキストストア。

## 3. 全体アーキテクチャ

```text
Mic / Discord / 画面 / 再生中メディア
        │
        ▼
Audio Front End
  AEC・ノイズ抑制・VAD・プリロール・音量正規化
        │ audio frames + timestamps
        ▼
Realtime Understanding
  partial STT / final STT / 音声感情 / 話者 / 終端予測
        │ observations
        ▼
Turn Manager ─────────────── World State Store
  聞く・待つ・相槌・割込・保留        会話、再生中曲、画面、ツール、ペルソナ
        │ turn decision + context snapshot
        ▼
Response Planner
  意図理解・回答計画・検索/ツール判断・話し方指示
        │ response plan + stream
        ▼
Speech Renderer
  文分割・TTS・Style Manager・再生キュー・ダッキング
        │
        ▼
Speaker / Discord VC / GUI
```

音声データはリアルタイム経路、会話履歴や人格は制御経路として分離する。LLMを待つ間も、Turn Managerは音声入力を継続監視する。

## 4. コンポーネント設計

### 4.1 Audio Front End

- 16 kHz mono float32を共通フォーマットにする。
- VAD開始の前に最低320 msのリングバッファを保持し、子音の語頭を失わない。
- ローカル再生時は、可能ならOSのエコーキャンセルまたはヘッドセット利用を優先する。ソフトウェアAECは後段フェーズで導入する。
- フレームには `stream_id`、単調増加時刻、音源種別、話者候補を付ける。

### 4.2 Realtime Understanding

partial STTは画面表示専用にせず、次の状態推定にも使う。

- `speech_probability`: 現在の発話確率。
- `end_of_turn_probability`: この発話が終わった確率。
- `intent`: 質問、指示、相槌、訂正、雑談、停止操作。
- `interruption_score`: AI発話を止めるべき確率。
- `emotion`: openSMILEとSpeechBrainで求めた感情確率。
- `stt_confidence`: 認識品質。低い時は確認質問または保守的な解釈にする。

Whisperの固有名詞対策は、初期プロンプト・hotwords・安全な後補正の三段構成にする。一般語を無条件に置換しない。補正辞書はユーザーごとに収集し、実測ログから追加できるようにする。

### 4.3 Turn Manager

Turn ManagerはLLMではなく、決定的でテスト可能な状態機械として実装する。

状態は `LISTENING`、`USER_SPEAKING`、`THINKING`、`ASSISTANT_SPEAKING`、`DUCKING`、`INTERRUPTED`、`WAITING_FOR_CONTINUATION` を持つ。

主な規則は次のとおりである。

- 相手が話し始めたら、AI音声を150〜300 msでダッキングする。
- 「うん」「はい」等の相槌はAIを復帰させ、応答を継続する。
- 意味のある質問・訂正・停止指示は、AI音声を200〜400 msでフェードアウトする。
- 未完のAI応答は要約してDeferred Topicへ保存し、横道の質問の後に復帰できるようにする。
- 相手の発話終了確率が高い時だけLLM生成を開始する。最終STTを待つ必要がある場合でも、準備処理はpartial STTから先行させる。

### 4.4 World State Store

短期会話履歴とは別に、現在世界で何が起きているかを構造化して保存する。

```json
{
  "active_persona": "poppo",
  "conversation": {"topic": "...", "deferred": []},
  "media": {"kind": "music", "title": "...", "position_s": 32.4},
  "screen": {"summary": "...", "captured_at": 0},
  "user": {"emotion": {"label": "neutral", "confidence": 0.82}},
  "assistant": {"state": "speaking", "response_id": "..."}
}
```

各ターンではこのスナップショットを短いsystem contextへ変換してLLMに渡す。メディアの曲名しか分からない時は、歌詞や特定の演奏箇所を聴いたふりで断定しない。音源分析を導入した場合だけ特徴量や区間情報を追加する。

### 4.5 Response Planner

LLMへの要求を一つにまとめず、構造化出力に分ける。

```json
{
  "intent": "answer",
  "content": "返答本文",
  "delivery": "warm",
  "emotion": "joy",
  "should_search": false,
  "should_resume_topic": false,
  "acknowledgement": null
}
```

- `content` はユーザーに話す本文。
- `delivery` と `emotion` はStyle Managerへ渡す。
- `should_search` は検索設計LLMを呼ぶ契機であり、ユーザー文をそのまま検索しない。
- `acknowledgement` はユーザーの発話終了後だけ使用し、毎ターンには付けない。

構造化出力に失敗した場合は、本文のみの通常応答へ安全にフォールバックする。

### 4.6 Speech Renderer

- LLMトークンを文境界で分割し、最初の確定文からTTSを開始する。
- Style Managerは、ペルソナ基準値、LLM指示、ユーザー感情、会話状況を合成して速度・高さ・抑揚・音量を決める。
- 再生キューは文単位でキャンセル可能にする。割り込み時は現在音声をフェードアウトし、未再生文を破棄する。
- 音楽再生中は、AI発話時だけダッキングし、通常時はユーザー指定音量を維持する。

## 5. レイテンシ予算

| 区間 | 目標 | 備考 |
| --- | ---: | --- |
| VAD終端の確定 | 150〜350 ms | 発話の自然さと応答速度のトレードオフ |
| final STT | 150〜350 ms | GPU、短い発話を前提 |
| 応答計画/LLM初回トークン | 150〜450 ms | 高速APIまたは常駐ローカル推論 |
| TTS最初の文 | 150〜350 ms | 文単位ストリーミング |
| 最初の音声再生 | 700〜1,300 ms | 通常会話の目標 |

各ターンでこの区間を計測し、p50/p95を記録する。改善対象は平均ではなくp95の遅延と、割り込み失敗率で評価する。

## 6. 音楽・動画を「一緒に聞く」設計

段階を分ける。

1. **再生メタデータ共有**: 曲名、検索語、再生位置、速度、音量をWorld Stateへ入れる。現在実装済みの基盤。
2. **外部知識補完**: 曲名から公式情報・作品情報を検索し、曲についての質問時だけ根拠付きで渡す。
3. **音源特徴量**: PCMを別タップし、区間ごとのエネルギー、テンポ、ボーカル有無、ムードを抽出する。TTSやSTTの入力と混ぜない。
4. **歌詞・意味理解**: 権利と取得元を明確にした歌詞データ、またはユーザー提供テキストだけを解析する。動画や曲を無断で文字起こしして保存しない。

ローカルの埋め込みYouTubeプレイヤーはブラウザのクロスオリジン制約によりPCMを直接取得できない。そのため本格的な音源特徴量は、バックエンドで取得した再生用ストリームを明示的に分析タップへ複製する構成へ移行する。

## 7. 実装ロードマップ

### Phase A: 対話制御の安定化

- Turn Managerを既存Pipelineから独立させる。
- partial STT、相槌、割り込み、保留話題のユニットテストを充実させる。
- 誤変換辞書・固有名詞ヒントをGUIで編集可能にする。

### Phase B: 低遅延化

- partial STTから終端予測と応答準備を行う。
- LLMの構造化応答とTTS文単位ストリーミングを接続する。
- ターン別レイテンシのp50/p95可視化を追加する。

### Phase C: マルチモーダル世界状態

- 音楽、動画、画面、ツール実行結果をWorld Stateへ統合する。
- メディア質問時だけ検索・特徴抽出を行い、不要な処理を避ける。

### Phase D: 音源理解と適応

- Discord/ローカル再生ストリームの分析タップを追加する。
- ユーザーごとの発話速度、呼びかけ語、補正辞書をペルソナごとに分離して蓄積する。
- AECとマイク・スピーカー同時利用時のエコー耐性を強化する。

## 8. 品質と安全の評価

- 割り込み成功率、相槌誤停止率、語頭欠落率、固有名詞正答率を回帰テストにする。
- 音源・画面・検索結果について、入力にない詳細を断定していないかを評価する。
- 誤変換辞書は、置換前後・時刻・使用回数をローカルログに残し、ワンクリックで無効化できるようにする。
- 個人の会話履歴、声紋、音源データはペルソナ・利用者・保存期間を分離して扱う。
