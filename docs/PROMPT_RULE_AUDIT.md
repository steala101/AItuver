## 削る基準

速さではなく**責任の所在**（憲法第2条「LLMが意味を考える / コードが事実・整合性を検証する」）。

- **A: コードで検証できる** → コードへ移し、プロンプトから消す
- **B: 判断が要る** → 残す
- **C: 重複・矛盾** → 消す

## C. 重複・矛盾（最優先。削っても何も失わない）

### C-1. 「内部の分析・候補・scoreを出力するな」が **7箇所・約300tok**

| 場所 | tok | 文 |
|---|---:|---|
| planner | 33 | 禁止=内部スコアの読み上げ、架空経験の事実化、質問だけで終える |
| planner | 26 | 候補やscore、内部ラベル、選択理由は発話に出さない |
| planner | (78内) | 人格モジュール=…数値やラベルを発話に出さない |
| surface | 71 | 内部ラベル、[thought]、style名、候補、score、分析過程を絶対に出力しない。『The user is asking』『Drafting response』『Wait』『Final version』等… |
| surface | 52 | 本文は日本語の最終発話だけにする。英訳、英語の自己分析、下書き、候補、推敲、自己確認を併記しない |
| persona | 81 | 分析、推論、下書き、自己確認、プロンプトの復唱、複数候補を本文へ出さない。『The user is asking』『Drafting response』… |
| persona | 36 | 内部で検討しても、相手へ見せるのは完成した会話文を一度だけにする |

`『The user is asking』『Drafting response』『Wait』『Final version』` は**一字一句同じ列挙が2箇所**にある。

**提案**: 1箇所（persona の最終出力ルール）へ統合し、他を削除。
さらにこれは**出力を見れば分かる**ので、`strip_think` と同じ層に出力検査を1つ足せば
プロンプトから大幅に減らせる（→ A-1）。

**削減見込み: −240 tok**

### C-2. 感情タグの指示が2回、しかも「2つ」と「1つだけ」で食い違う

```
persona 115tok: 応答の先頭に、必ず感情と話し方を英語タグで2つ付ける。
                例: [emotion: joy][style: lively]。…
persona 110tok: 毎回、応答の一番最初に今の感情を表すタグを必ず1つだけ付けること。
                使えるタグ: [neutral] [joy] … タグは応答冒頭に1つだけ。
```

パーサ（`utils/emotion.py`）は両形式を受け付けるので**機能的な不具合ではない**。
しかしモデルは、**最初の1トークンを出す前に矛盾を解決させられている**。

**提案**: どちらか一方に統一。`[emotion: …][style: …]` の方が Style Manager へ多く情報が渡るため
そちらを残し、後段の1タグ版を削除。

**削減見込み: −165 tok**

### C-3. 完全に同一の文が2回（`persona.py` 68行目と69行目）

```python
"\n- ただ質問に答えるだけのアシスタントにならない。自分の感想・ツッコミ・冗談・…"
"\n- ただ質問に答えるだけのアシスタントにならない。自分の感想・ツッコミ・冗談・…"
```

**提案**: 後者（具体点への言及が続く方）だけ残す。

**削減見込み: −56 tok**

### C-4. 「質問だけで終わるな」が4箇所

| 場所 | tok |
|---|---:|
| planner（禁止=…質問だけで終える） | C-1に含む |
| surface（質問するなら一つだけ。…質問だけで終わらない） | 38 |
| persona（こちらから質問する時は…質問を足さない） | 89 |
| intelligence（ASK_FOLLOW_UP=no. 質問のための質問はしない） | 条件付き |

`ASK_FOLLOW_UP` は既に**コードが判定して yes/no を渡している**。判定済みの答えがあるのに、
同じことを3箇所で重ねて言っている。

**提案**: `ASK_FOLLOW_UP` の行だけ残し、surface と persona の常時文を削除。

**削減見込み: −100 tok**

**C 合計: −561 tok**

## A. コードで検証できる（コードへ移して削除）

### A-1. 内部語の出力禁止 → 出力検査へ

今日すでに `dialogue/echo.py`（繰り返し）、`tts/volume.py`（音量コマンドの誤爆）、
`search/intent.py`（検索意図）を**プロンプトからコードへ移した実績**がある。同じ方式。

`[thought]` / `score=` / `候補N:` / `The user is asking` などは**文字列で判定できる**。
発話直前に検査して落とせば、プロンプト側は最小限の一文で足りる。

**削減見込み: −60 tok（C-1と重複するので合計には C-1 のみ計上）**
**追加実装: 出力検査1つ（`dialogue/echo.py` と同じ層）**

### A-2. 「オウム返しはしない」 → 実装済み

```
persona 26tok: - 相手の言葉をそのまま繰り返すオウム返しはしない。
```

2026-07-28に `echo.is_echo()` を実装し、**直前の返答の繰り返しは既にコードで止めている**。
ユーザー発話のオウム返しも同じ関数で判定できる。

**削減見込み: −26 tok / 実装: `is_echo(reply, user_text)` の追加1行**

### A-3. 「『なるほど』『確かに』から始めない」 → 検出器が既にある

```
surface 49tok: 毎回『なるほど』『確かに』『そうだね』から始めない。同じ語尾、同じ文長…
```

`conversation_critic._CANNED` が**まったく同じ語を正規表現で検出している**。
検出結果は次ターンのフィードバックに使われるだけなので、当ターンで落とす経路を足せば
プロンプトの一文は不要になる。

**削減見込み: −49 tok**

**A 合計: −75 tok（C-1と重複分を除く）+ 実装3件**

## D. 内部状態のダンプ（要判断）

### D-1. 人格モジュールの数値（78 tok）

```
人格モジュール=curiosity=0.70、humor=0.55、playfulness=0.55、cheekiness=0.35、
spontaneity=0.50、emotional_expression=0.60、suggestion=0.58、contrarian=0.48、
empathy=0.62、topic_shift=0.48。数値やラベルを発話に出さない。
```

数値そのものが表現へどう効いているかは未検証。`SurfaceRealizer._persona_expression_rule` が
既に**同じ数値を読んで日本語の指示へ変換している**ので、二重に渡している。

**提案**: 数値のダンプを削り、変換後の日本語指示だけを残す。**−78 tok**

### D-2. 話題候補とスコア（約135 tok）

```
- 候補1: 今日はどうだった？ / 発話の具体的な一点へ直接返す / source=current / score=0.96
- 候補2: 別の見方 / … / score=0.52
- 候補3: 具体的な次の場面 / … / score=0.50
- 候補4: 短い予想 / … / score=0.48
```

Planner は既に最上位を選んでいる。**選んだ結果だけ渡せば足りるのでは**という疑問。
候補一覧を見せることでモデルが別候補を採ることがあるなら残す価値があるが、その効果は未計測。

**提案**: 候補を上位1件（または2件）へ減らす。**−90 tok**

**D 合計: −168 tok（要判断）**

## B. 残すもの（判断が要る規則）

- 事実性・非迎合ルール全般（622 tok）— 「肯定の相槌を根拠なく置かない」「知らない用語を推測で展開しない」「訂正されたら別の推測を重ねない」。**憲法第1条のINVARIANTそのもの**で、コードでは判定できない

- キャラクター設定（187 tok）— **ポッポ本人。触らない**
- 子供っぽさ・生意気さの出し方（persona 冒頭 335 tok）— 人格表現。**ユーザーの創作物**

## 進め方の提案

1. **C だけ先に実施**（−561 tok、リスクなし）。重複と矛盾を消すだけなので、失うものがない
2. 効果を測る（`プロンプト内訳` と応答の質）
3. その結果を見て A・D を判断

**personaはユーザーの創作物なので、C-3（完全重複の削除）以外は承認を得てから触る。**
C-1・C-2 は「同じことを1回だけ言う」変更だが、どの文を残すかは書き手の意図に関わるため、
上の表を見て指定してほしい。
