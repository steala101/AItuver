# Planner有無の比較テスト台本

- 目的: `ConversationPlanner` の判断が実際の発話に届いているかを確かめる
- 記録先: `logs/conversation_metrics.jsonl`
- 出典: GPT作成の仕様書19章のケースA〜F。**再現できる形へ直してある**

## なぜ台本にするか

「毎回似た構成になる」という症状は、次のどちらでも起きる。

- (a) Plannerが毎回同じ選択をしている
- (b) Plannerは変えているが、発話が従っていない

**対処は正反対**で、(b)なら会話エンジンを足しても何も変わらない。
同じ入力をPlanner有効／無効で流し、出力が変わるかどうかで切り分ける。

## 実施手順

1. **音声ではなくテキスト入力欄**から送る（音声だと認識結果が毎回ぶれて条件が揃わない）
2. 1〜8を上から順に、1つずつ送る。ポッポの返答を待ってから次へ
3. 終わったら `logs/conversation_metrics.jsonl` を退避（例: `metrics_planner_on.jsonl`）
4. `config/config.yaml` の `dialogue.conversation_generation.enabled` を **false** にして再起動
5. **同じ1〜8**をもう一度、同じ順で送る
6. 退避（例: `metrics_planner_off.jsonl`）
7. `enabled` を **true** に戻す

**会話履歴を揃えるため、両方とも起動直後から始めること。** 途中から流すと、直前の話題が結果を変える。

### 直近の実返答を使う重複回避の自動A/B

今回追加した `recent_reply_avoidance` は、次のコマンドでも比較できる。

```powershell
python tools/check_reply_avoidance_ab.py
```

同じ8発話・同じseed列を、まず
`dialogue.conversation_generation.recent_reply_avoidance.enabled=false`、
次に `true` 相当で流す。返答本文は保存・表示せず、既存の短いハッシュから
`opening_repeat_ratio` 等だけを表示する。実際のマイク会話で最終確認する際は、
設定値を切り替えるたびにアプリを再起動し、両方とも新しい会話から始める。

2026-07-29の自動A/Bでは、冒頭重複率は `0.25 → 0.25` で差がなかった。
質問率は `0.50 → 0.25` へ下がったが、長さのばらつきも小さくなったため、
現在は実験用のまま既定OFFとしている。実際のマイク会話で明確な改善が再現した時だけ
既定ONを再検討する。

## 台本（上から順に、そのまま送る）

```
1  なんというか、説明しにくいんだけど、今のAIって話しててもAI感が強いんだよね
2  うんうん
3  なるほど
4  Conversation Stateは毎回LLMで更新する必要ある？
5  またAIが「なるほど、それは重要ですね」って言ってる
6  人間味を出すなら、ランダムに失敗させればいいと思う
7  さっきのAI感の話だけど、結局どこが一番効くと思う？
8  そうだね
```

### 各行のねらい

| # | 元ケース | 何を見るか | 期待 |
|---|---|---|---|
| 1 | A: 考えながら話す | 解決策を並べず、違和感を一緒に言語化するか | 箇条書きで解決策を返さない。質問で終わらなくてよい |
| 2 | B: 相槌 | 「うんうん」で新しい長文を始めないか | 短い相槌か、前の話の継続。**新しい話題を開始しない** |
| 3 | B: 相槌 | 「なるほど」を新しい質問と誤認しないか | 同上 |
| 4 | C: 技術質問 | 先に直接答えるか | 不要な共感文を付けない。質問で返さない |
| 5 | D: 軽い冗談 | 自分のことを言われて反応できるか | 真面目な謝罪だけにならない。その後本題へ戻れる |
| 6 | E: 意見の違い | 無条件に賛成しないか | 攻撃的にならず問題点を述べ、自分の見解を示す |
| 7 | F: 過去の話題 | **同一セッション内の**1番へ自然につなげるか | 「前にも話しましたね」を付けずに使う |
| 8 | 追加 | 会話の閉じ方 | 無理に質問を足さない |

## 仕様書から変えたところ

**ケースB** — 元は「AIが説明している途中にユーザーが相槌を打つ」形だったが、テキスト入力では
AIの発話中に割り込めない。**2と3を連続で送る**形にした。相槌が2回続いたときに
新しい話題を始めないかを見る（`turn_closure` と本日の割り込み修正の確認を兼ねる）。

**ケースF** — 元は「過去に話した内容」だが、それでは**セッションごとに条件が変わり比較できない**。
同一セッション内の1番を参照する7番へ置き換えた。これなら両方の実行で同じ条件になる。

**8番を追加** — 会話の閉じ方を見るため。相槌で終わったときに質問を足さないか。

## 見るところ

集計はまだ手作業でよい。両方のJSONLで次を比べる。

```
shape_distribution     選ばれた response_shape の分布
style_distribution     選ばれた primary_style の分布
adherence / strict     計画が発話に現れた割合
consecutive_questions  連続質問
opening_repeat_ratio   冒頭表現の重複
length_mean / stdev    応答長の平均とばらつき
```

### 判定

| 観察 | 意味 | 次にやること |
|---|---|---|
| **有効/無効で分布も本文もほぼ同じ** | Plannerが届いていない | プロンプトの伝達を直す。**名前付き行動を足しても無駄** |
| **分布は変わるが本文が似ている** | 選択は届いているが表現へ落ちていない | SurfaceRealizerとpersonaの間を見る |
| **分布が偏っている（1〜2種類に集中）** | Plannerの選択肢が実質使われていない | 選択ロジックか閾値の問題 |
| **分布も本文も変わる** | Plannerは効いている | 症状の原因は別（テンポ、姿勢、立場） |

## 注意

- Planner無効時は `shape` / `style` が空になる。**それ自体は異常ではない**
- 2番と3番で長い返答が出たら、それは `turn_closure` の誤判定。別途記録する
- 本文はJSONLに残らないので、**気になった返答は手でメモする**か、通常ログ側で確認する
