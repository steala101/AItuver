## 設計

### なぜ「確率でたまに入れる」にしなかったか

確信しているのに「うーん……」と言うのは、知識と能力を実際より低く見せる**偽装**である。憲法第1条の`INVARIANT`が明示的に禁じている:

> 人間らしく見せるために、知覚・記憶・感情・経験・能力・検索結果を偽ってはならない。

同時に、同条は「『覚えていない』を自然に言えることは品質の一部である」とも言っている。つまり**本当に迷っている時に迷いが声に出ること**は、この憲法が求めている方向そのものである。乱数で撒くのはその逆になる。

### 役割分担（第2条）

```
コードが「迷う理由があるか」を確定する   ← 既存の信号から、事実として
LLMが「文のどこが迷いどころか」を決める   ← 意味を知っているのは書き手だけ
コードが「間と話速」を音にする            ← 検証できる機械的処理
```

判定材料は**すべて既に他の目的で計算されている値**で、この機能のために新しい推論を足していない（D-017）:

| 信号 | 出所 |
|---|---|
| 聞き取りが怪しい | `Transcript.uncertain_words` / 語ごとの確率（STT補正） |
| 指すものが特定できない | `TurnFrame.reference_resolution.requires_clarification`（Kernel） |
| 思い出せない | 記憶検索のヒット数 |
| 根拠がない | `SearchDecision.allowed` / `blocked_by_context` |
| 意見が定まらない | 依頼文の形 |

### 仕草の運び方

内部タグを使わない。ユーザーの選択どおりチャットにも同じものを出すため、キャリアは**普通の日本語**である必要がある。`「……」`をそのまま使う——表示しても自然で、剥がす処理が要らず、内部語がTTSへ漏れる事故（第1条 1.4）が構造的に起きない。

### 判定の要点

- **確信している時は明示的に禁止する。** 何も言わないと、前のターンの許可がモデルの中に残る。「今回は迷っている点がない。言い淀みを入れない」と毎回言う。
- **既定は1回、2回は複数の意味で迷った時だけ。** 1文ごとに詰まる人は思慮深いのではなく壊れている。
- **直前のターンで既に仕草が出ていたら抑制する。** `count_gestures()` が直近の発話を数え、`recent_gestures` として減衰させる。
- **許可文に「えっと」「うーん」を書かない。** 例示すると口癖になる。書くのは**状態の説明**（「思い出そうとしているが、はっきりしない」）だけで、表現はモデルが選ぶ。

### 送出の要点

- `「…」`の長さが無音の長さになる（1つ=320ms、上限900ms）。人が書く通りの直感と一致する。
- 言い淀み部分**だけ**を0.88倍の話速にする。返答全体を遅くしない。
- 「〜かな」「〜けど」で言い切らずに終えた文の後に一拍(220ms)。これがないと考えている風でなく切れた風になる。
- 「……」のない文は**従来どおり1回の合成**で処理する。通常経路のコストはゼロ。
- 何も足さない。`plan_delivery` は流暢に読める文へ間を挿入しない。「間を入れるべきか」の判断は上流にある。

### フィラー判定の罠

`^あ` は「ありがとう」に、`^そうだね` は「そうだね、それは面白い」に当たってしまう。前者は挨拶、後者は同意であって、どちらも言い淀みではない。短いフィラーは**単独で立っている時のみ**（後ろが句読点か文末）を条件にし、伸ばした形（`あー` `そうだねぇ`）を要求した。長い語（「なんて言えば」等）は曖昧でないので条件なし。

## 変更しなかったもの

- `SurfaceRealizer` の既存規則。「軽い言い直しは考え直す場面だけ低頻度で」はそのまま残し、その「場面」の判定材料を外から渡す形にした。
- `_MODE_GUIDE` やペルソナ。人格側へ「詰まれ」と書くのは D-016 が戒める方向で、しかも常時適用されてしまう。

## 憲法・ADRへの影響

- 第1条 `INVARIANT`（能力を偽らない）: この機能の設計根拠そのもの。確信時に禁止する分岐がその実装。
- 第1条 1.2（固有で成長する人格）: 「人間らしさを全肯定、無根拠な馴れ馴しさ、架空の思い出として表現してはならない」と同じ考え方を、話し方の側へ適用した。
- 第1条 1.4（内部thoughtを漏らさない）: `「……」`をキャリアにしたので、剥がし忘れによる漏洩が構造的に起きない。
- 第2条: 意味の判断はLLM、状態と検証はコード。
- D-016: 表現をコードで固定せず、許可として渡す。
- D-017: 判定に追加のLLM呼び出しを使わない。

## 次の担当への注意

- **許可文へ「えっと」「うーん」などの具体例を書かないこと。** 例示は口癖になる。書くのは状態の説明だけ。
- `assess()` へ新しい信号を足す時は、それが**実際に計算されている事実**か確認すること。「たぶん難しい話題だから」のような推測を足すと、この機能は偽装に戻る。
- `plan_delivery` に「文が長いから間を入れる」といった生成的な規則を足さないこと。この関数は書かれたものを音にするだけで、書くかどうかは決めない。
- 実機受入項目: (a) 普段の会話で仕草が出すぎていないか、(b) 聞き取りが怪しいターンで実際に出るか、(c) 間の長さが不自然でないか、(d) チャット表示と声が一致しているか、(e) ログの`今回の確信度`と実際の発話が対応しているか。
