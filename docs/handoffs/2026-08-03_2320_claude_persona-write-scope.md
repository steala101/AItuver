## 2. さらに見つかったこと

`EpisodicMemoryService.bind_persona()` は Phase 7C で作られていたが、
**呼び出し側が無かった。** つまり:

- 読み側の絞り込み → `persona_id` が空で、絞っていない
- 書き込み側の持ち主 → 空のまま溜まる

またしても「実装がある」と「効いている」の差。ここも故障注入ではなく
**実機ログ**で見つかった——`logs/neuro_voice.log` に
`長期記憶の埋め込みをメモリへ展開: 記憶0件` が並んでいた。

## 3. 直したこと

**持ち主を決める場所を `MemoryStore` の1箇所にした。**

```
MemoryStore.bind_persona(persona_id, strict=...)
  └ _owner(persona_id, scope) → (持ち主, スコープ, 書いてよいか)
       add() / add_episode() / save_reflection() が全部これを通る
```

呼び出し側に任せると、経路が増えるたびに `persona_id` が空の記憶が
生まれる。判断を2箇所に置くと必ず食い違う。

`Mind._bind_persona_scope()` を、`EpisodicMemoryService` を作る
**2箇所とも**（初期化・ペルソナ切替）から呼ぶ。

**仮説にも持ち主を付けた。** 仮説は複数の記憶から作られるので、
元の記憶が分かれていても仮説が共有だと、そこから逆に漏れる。
`reflections` に列が無い既存 DB のための移行も入れた——
`CREATE TABLE IF NOT EXISTS` は既にある表へ列を足さないので、
無いまま開くと保存が `OperationalError` で落ちる。

## 4. 決めた境界（理由つき）

| | 挙動 |
|---|---|
| 持ち主を付ける | **フラグに関係なく必ず。** 空のまま溜めると、あとで分離を有効にした瞬間に全部隠れる |
| 持ち主不明の私的記憶 | `persona_scope_enabled: false` → **保存して警告のみ**／true → **保存しない** |
| スコープ未指定の古い呼び出し | **拒否しない。** まだ直していない経路の記憶が黙って消えるのを避ける |
| 共有3スコープ | 持ち主不要（世界状態・ツール定義・明示共有） |

拒否を無効時にもやらない理由: `persona_scope_enabled` が false の間は
持ち主が空でも検索条件に入らないので**読める**。そこで拒否すると、
分離のためではなく**読める記憶を落とす**ことになる。

## 6. チビへ: 計測のやり直し手順

前回は下の2つが false だったので、記憶検索が一度も動いていなかった。

```yaml
memory:
  retrieval_enabled: true       # ← 上げる
  reflection_enabled: true      # ← 上げる

turn_integrity:
  turn_frame_enabled: true      # ← 記録のみ・挙動は変わらない
  persona_scope_enabled: false  # ← **まだ false のまま**
```

`persona_scope_enabled` を今回上げないのは、**古い記憶（持ち主が空）が
全部隠れる**から。今回の変更で**これから作られる記憶には持ち主が付く**
ので、しばらく会話して新しい記憶が溜まってから上げる方が、
「隠れた」のか「分離が効いた」のかを取り違えない。

### 手順の訂正

前回のログでは、`a` を**削除した後**に合言葉5件を教えていた。
記憶は `b` に入っていた。テスト用ペルソナは**削除せず**、
教える前に 🩺 で `active_persona_id` を確かめてほしい。

### 確認したいこと

1. 合言葉5件を教えた後、その DB の `memories` が **5件前後になる**
   （前回は 0 件だった）
2. その行の `persona_id` が**空でない**
3. 別ペルソナへ切り替えた後、`memories` が**別ファイル**で、
   合言葉を知らない

3 は前回も「知らない」と答えていたが、**Memory が空だったので
意味が無かった。** 今回は中身がある状態で確かめられる。
