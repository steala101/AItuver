## 目的

「ネウロ様やEvilと比べると会話のテンポ、受け答えのセンスが届いていない」への対応として始めた遅延調査を、結論まで持っていく。

## 結論: 3.5秒の内訳

```
600ms   Ollamaのリクエストごとの固定処理  ← 設定では動かせない
300ms   我々のクライアント側（SDK・ストリーミング）  ← 未調査
1350ms  プロンプト評価（未キャッシュ約5600tok × 0.244ms）
1000ms  STT・文脈・話者・TTS
─────
3500ms
```

実測式（40サンプル）:

```
初トークン ≈ 1106ms + 0.244ms × (キャッシュされなかったトークン数)
```

## 見つけて直したもの

### 1. `keep_alive` が一度も送信されていなかった

`llm.keep_alive: 10m` は設定され、コンストラクタも受け取っていたが、`_multimodal_keep_alive` にしか保持されず**リクエストに入っていなかった**。Ollamaは自前の5分既定でモデルを落とすため、**5分以上の沈黙のあとの1発目が丸ごと再ロード待ち（実測6.9〜7.9秒）**になっていた。

プローブで `keep_alive: 30m` を明示指定したところ期限が 23:39 → 00:05 へ動き、リクエストに入れれば効くことを実証済み。

### 2. プロンプト配置（効果は限定的だった）

毎ターン変わるブロックが index 1（personaの直後）に挿入されており、再利用できるのはpersonaの2296トークンだけだった。13箇所を `insert_before_user_turn()` へ統一。ただし**再利用率は28〜32%のまま**で、今度は会話履歴が壊していることが判明した。さらにその履歴の切り詰めは、systemブロックだけで5000〜6000トークンあり**プロンプトが一度も予算に収まらない**ため毎ターン切り直しになる。プロンプト側に残る手段は `Mind.build_context` の5000tokブロックを小さくすることだけ。

## 失敗した試行

**この調査中に、私は同じ形の誤りを5回している（R-037）。**

1. `AudioDeviceMonitor` の既定 `refresh=True` — 1回の遷移は正しいが、3秒ごとに繰り返した時にPortAudioを再初期化してマイクとTTSを殺した
2. 区間の `WAIT` — 1回は正しいが、繰り返すと90秒で20回の空回りになった
3. `note_suppressed_user_turn` — 手番を返した先で2番の空回りを引き起こした
4. プローブの設定キー — 隣に正しく読んでいる `factory.py` があるのに推測で書き、1行も出力されなかった
5. `keep_alive` の追加 — **サーバがないと一度も実行されないコード**に存在しない属性名を書き、**全応答を停止させた**

共通するのは「**実行して確かめられる形にせずに書いた**」こと。5番の修正で `request_extra_body()` を切り出したのは、その対策を実際にやったもの。属性名を1文字変えると新規テストの8件が落ちる。

加えて、集計自体が嘘をついた例が1つある。num_ctx掃引の結果を平均したため、掃引が自分で起こした再ロード（7秒）と定常値（600ms）が混ざり、`3624/4088/3767ms` という何も意味しない数字を判定の根拠として出した。最小値へ直し、再ロード費用は別行で報告するようにした。
