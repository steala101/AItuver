## 調査結果

### 実測から得た式（40サンプル、`logs/neuro_voice.log` 2026-07-27）

```
初トークン ≈ 1114ms + 0.241ms × (キャッシュされなかったトークン数)

  未キャッシュ  442tok →  実測1121ms / 予測1220ms
  未キャッシュ  463tok →  実測1101ms / 予測1225ms
  未キャッシュ 6004tok →  実測2510ms / 予測2562ms
  未キャッシュ 7379tok →  実測2748ms / 予測2894ms
```

この式が意味すること:

1. **プロンプト評価は実在する**。未キャッシュ分に比例して増える。並び替えには意味がある。
2. **しかし1114msの固定費がある**。未キャッシュ442トークン（評価はおよそ100ms）のターンでも1121ms待っている。**約1秒がプロンプトと無関係に消えている**。

当初「遅延の主因はプロンプト評価」と説明したが、**これは半分誤りだった**。プロンプトを完璧にしても 1114 + 240 ≈ 1350ms が残り、合計2.3秒にしかならない。

### 1114msの候補

未検証。切り分けのための計測を追加した。

- モデル常駐が切れて毎回ロードし直している
- リクエストごとに `options.num_ctx` を渡しており、KVキャッシュが再確保されている
- 視覚・記憶の埋め込みが同じサーバを取り合って順番待ちしている（D-017）

## 追記: 配置修正後の実機結果（2026-07-27 22:20〜22:24）

### 分割は狙いを外した

```
LLM内訳: 接続=2450ms / 生成=0ms / 同時実行=1 / 待ち=0ms
```

`生成=0ms` は「サーバが最初のトークンを作り終えるまで応答を返さない」という意味で、待ち行列とプロンプト評価は分離できなかった。ただし2つ確定した。

- **同時実行=1・待ち=0ms が全ターン** → 我々のリクエスト同士の競合ではない
- **未キャッシュ464tok（評価≒113ms）でも1138ms** → プロンプト評価でもない

係数は前回と同一で `接続 ≈ 1106ms + 0.244ms × 未キャッシュtok`。残るのはOllama内部のリクエストごとの準備であり、毎回送っている特殊なものは `options(num_ctx/num_predict)` だけ。`llm.send_ollama_options: false` で切れるようにした（**既定は true のまま。まだ何も変えていない**）。

### 配置修正は目的を達していない

```
再利用可=2687tok (34%)  最初に変わった所=assistant
```

systemブロックの並びは直った（`最初に変わった所` がsystemでなくなった）が、再利用率は30〜35%のまま。今度は**会話履歴**が壊している。毎ターン予算ぎりぎりまで切り詰めるため、残る最古のメッセージが毎回変わり、personaの直後から食い違う。

これは私が「やるべき」と書きながら実装していなかった3つ目である。`fit_messages(slack_ratio=)` を追加し、余裕を持って切ることで数ターン切り直さずに済むようにした。

### 現時点の正直な見通し

配置と切り詰めが両方効いても、`1106ms` の固定費が残るため合計2.3秒程度。**1秒には届かない。** 固定費の正体が判明しない限り、プロンプト側でこれ以上詰めても意味が薄い。

## 次の担当への注意

- **実機ログの `LLM内訳` を最初に見ること。** `接続` が1秒近ければ、プロンプトをどれだけ削っても無駄で、モデル常駐・待ち行列・KVキャッシュ再確保の側を直す必要がある。
- `insert_after_stable_prefix` は**毎ターン完全に同一の文字列にだけ**使うこと。少しでも変わるものを入れると、プロンプト全体のキャッシュを壊す（このモジュールが存在する理由そのもの）。
- 新しいsystemブロックを足す時は `insert_before_user_turn` を使うこと。`[messages[0], ...]` の形を復活させない。
- 実機受入項目: (a) `再利用可` の割合、(b) `LLM内訳` の 接続／生成 の比、(c) `同時実行` と `待ち`、(d) 初トークンの p50 が2464msからどう動いたか、(e) 応答内容が以前と変わっていないこと（配置変更のため原理的には変わらないが、モデルは位置に敏感なので確認する）。
