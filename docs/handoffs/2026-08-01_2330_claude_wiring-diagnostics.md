## 1. なぜ「読むだけ」の点検にしなかったか

Phase 4 の監査で `CognitiveState.irritation` が実装以来ずっと 0.0 を返して
いたことが分かった。その時点で揃っていたもの:

- 実装がある
- テストが通っている
- 設定も入っている
- ログにもエラーが出ない

**値だけが届いていなかった。** `TemporalSelf.snapshot()` は感情を `"affect"` の
下に入れて返し、`AffectState` の軸名は `frustration`。階層が1つ違い、名前も
違っていた。テストは `build_state(affect={"irritation": .8})` と直接渡していた
ので通っていた——**実際の呼び出し側と違う形で検証していた。**

設定値やフラグを一覧するだけの画面では、これは絶対に見つからない。
だから各プローブは**一往復させる**。

```
目印の値を入口へ入れる（合成データ）
  → 本番と同じ経路を通す
  → 出口で目印が読めるか見る
```

## 2. 6つの状態

| 状態 | 意味 |
|---|---|
| `OK` | 値が最後まで届いた |
| `OFF` | フラグで止めてある。**正常** |
| `BLOCKED` | ポッポが起動していないので確認できない（DBの中身など） |
| `BROKEN` | **フラグは入っているのに値が届かない。** いちばん見つけたいもの |
| `DISCONNECTED` | **実装はあるが読む側が無い。** 上げても効かない |
| `ERROR` | 点検そのものが失敗した。測る側の問題かもしれない |

**`OFF` と `BROKEN` を混ぜないこと**が設計の要。混ぜると
「赤が多いのはフラグを上げていないからだろう」で本物の故障が埋もれる。

そのため**点検はフラグと独立**に走る。合成データの一往復なので、
フラグが off でも配線の生死は分かる。フラグの状態は別の帯で見せる。

「◯◯が動いているか」だけだと、赤くなった時に慌てるか無視するかの
どちらかになる。

## 6. テストの方針

**全部緑になるテストは書かない。わざと壊した時に赤くなることを書く。**

この作業中に「測る側が壊れているのに、測られる側の欠陥として報告した」のを
3回やっている。診断を入れるなら、診断自体を先に点検する。

9通りの故障を注入して赤くなることを確認:

- `irritation` の退行（入れ子と別名の吸収を外す）
- 関係性の軸の欠落
- 記憶が行動の点数を動かさなくなる
- 挨拶が保存され始める
- **感情が警告へ届く**
- **沈黙が罰として使われ始める**
- 終了合図が義務に再び隠される（Phase 4 preflight の再発）
- 1件のエピソードで仮説を作る
- 根拠のない操作指示が素通りする

加えて:

- 1つのプローブが例外で落ちても他は続く（第17条）
- **点検が実際の記憶を書き換えない**
- スナップショットが JSON 化できる
- 全掃引が 250ms 未満（3秒ポーリングの前提）

## 7. 途中で見つけた実物の欠陥

`derive_conversation_strategy(episodes, *, min_support=MIN_SUPPORT)` の
デフォルトが**定義時に束縛**されていて、`MIN_SUPPORT` を変えても効かなかった。
診断テストが `monkeypatch.setattr(reflection, "MIN_SUPPORT", 1)` で赤くならず、
そこで発覚。`min_support=None` にして中で解決するよう直した。

「定数を直したのに挙動が変わらない」はいちばん時間を溶かす種類のバグ。

## 8. 使い方

```
GUI 右上の 🩺 → 開いている間は3秒ごとに更新
⟳ で即時再点検
```

読み方:

1. **赤（届いていない）があれば最優先。** 何が起きるかは行に書いてある
2. **黄（読む側が無い）** は「上げても効かない」。フラグを上げる前に見る
3. **フラグ帯の ⚠** は上位が off で効かないもの
4. 灰（止めてある）は正常。減点していない
