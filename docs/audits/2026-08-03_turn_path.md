# 実経路の地図（Phase 7D 前）

- 日時: 2026-08-03
- 範囲: **通常会話1ターンが実際に通る所だけ**。使われていない旧経路は除く

---

## 結論を先に

**計測の背骨は既に実経路にある。** `neuro_voice/utils/latency.py` の
`TurnMetrics` が `pipeline` と `bot` の両方で使われており、
`LatencyWindow` が p50/p95 を 🩺 へ出している。

Phase 7C で作った `TurnLatency` は**この既存の背骨と二重**になる。
新しい計測系をもう1つ作るのではなく、**既存の `TurnMetrics` を
拡張する**のが正しい（第35項「既存基盤を再利用」）。

そして、既存の背骨に**終点の誤り**が見つかった（下記）。

### 誤りその1（`pipeline.py:2690`）

`_respond_direct_text()` は

```
synthesize() が返る
→ metrics.mark("tts_first")
→ metrics.mark("play_start")   ← **まだ鳴っていない**
→ self._playback.play(...)
```

**音声生成の完了を再生開始として記録している。** ここを通るのは
制御応答とゲーム攻略の即答経路。ストリーミング経路
（`_speak_loop`）は callback を使っていて正しいので、
**同じ `play_start` という名前に、意味の違う2つが入っている**。

`tts_first` と `play_start` が常に同じ値になるので、
「再生開始」の区間が 0ms として集計され、**合計も実際より短く出る。**

| 段階 | 実ファイル・実関数 | 同期 | 既存 mark |

| 受信〜ASR | `bot.py` の音声受信経路 | async | `speech_end` / `stt_done` |

| TTS | `bot.py:4970` | async | `tts_first` |

| 送出（Opus） | `self._source.write(pcm)` (`bot.py:4990`) | 同期 | `play_start` ❌ |

### 誤りその2（`bot.py:4997`）

`self._source.write(pcm)` は **Opus ソースのキューへ積むだけ**。
その後に `vc` の再生再開処理がある。**積んだ時刻を再生開始として
記録している。**

DAVE 側（`:4982`）は `await play_pcm()` の後なので、サイドカーへ
渡し終えた時点。実際に鳴った時点ではないが、Opus 側よりは近い。

## turn_id を渡せる地点

現状 `TurnMetrics` は**識別子を持っていない**。ターンをまたいで
区別する手段が `response_id` しかなく、`response_id` は
LLM 応答ごとに作られるので**発話確定の時点では存在しない**。

`speech_end` を打つ所（`pipeline.py:995` / `:1350`、`bot.py` の対応点）
が、`turn_id` を作れる最初の地点。そこから
`metrics` オブジェクトが `_speak_loop` まで引数で運ばれているので、
**`TurnMetrics` に `turn_id` を持たせれば、既存の受け渡しに乗る。**

---

## 通っていない段階の扱い

現在の `delta_ms()` は、片方の mark が無ければ `None` を返し、
`report()` と `LatencyWindow` が**その区間を飛ばす**。

つまり「通らなかった」と「測れなかった」が同じ扱い。記憶検索を
しなかったターンと、記憶検索が壊れて mark が打たれなかった
ターンが**区別できない**（第3項の `not_applicable`）。

---

## この監査から出る作業

1. **`play_start` の意味を1つにする。** `tts_audio_ready` を分け、
   `play_start` は実際に鳴り始めた所だけにする。
2. `TurnMetrics` へ `turn_id` と単調増加時計、`not_applicable` を足す。
3. Discord 固有の区間を、同じ構造の任意フィールドとして足す。
4. `TurnCommitLedger` を発話経路へ挿す。

**新しい計測系は作らない。** Phase 7C の `TurnLatency` は集計側
（p50/p90/p95・機能別比較）として残し、実測値は `TurnMetrics` から
流し込む。
