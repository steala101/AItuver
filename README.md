# Neuro Voice AI

> 開発者・AI開発エージェントは、変更前に [ポッポ開発憲法](docs/PROJECT_CONSTITUTION.md)、[現行アーキテクチャ](docs/CURRENT_ARCHITECTURE.md)、[Code Map](docs/CODEMAP.md) を確認してください。

ChatGPT Voice のような低遅延リアルタイム音声会話AI。Windows + RTX 5070 Ti を対象に、
Cerebras の高速推論とローカル STT/TTS を組み合わせて応答開始 1 秒前後を目指す。

## アーキテクチャ

```
Microphone → VAD (Silero) → STT (faster-whisper) → ConversationManager
    → LLM (Cerebras / OpenAI互換) → 文分割 → TTS (Qwen3-TTS) → Speaker
```

- 全モジュール asyncio Task + Queue 接続の疎結合構造
- LLM は `generate(messages)` だけ実装すれば追加可能 (OpenAI互換APIは設定変更のみ)
- 会話制御: AI発話中の入力を **相槌 / 割り込み / 誤検知** に分類。短い「うん」「はい」では止まらず、意味のある発話だけで中断
- AI側の相槌: ユーザーの発話が終わってから、応答の先頭へ「うんうん」「うーん」等を適度に添える
- 割り込み時の話題保留: 横道の質問へ答えた後も、元の説明を会話コンテキストとして保持し、「さっきの続き」で自然に再開
- Live風の割り込み: ユーザーが話し始めるとAI音声を一度小さくし、相槌なら復帰、実際の割り込みなら短くフェードアウト
- LLM駆動の話し方: LLMが各応答で感情・話し方タグを選び、StyleManagerがVOICEVOXの速度・音高・抑揚・音量へ変換
- 文単位ストリーミング: LLM出力の文が確定するたびにTTS→再生 (生成完了を待たない)
- 各段レイテンシ (STT / LLM初回 / TTS初回 / 再生開始 / 合計) を毎ターン表示・記録

## Gemma 4 マルチモーダル・映像認識

Gemma 4 は画像・映像理解とテキスト生成に使います。**音声を合成するTTSではありません**。読み上げは引き続きVOICEVOX（またはQwen3-TTS）を選んでください。

1. Ollamaへモデルを導入し、`ollama list` で正確なモデル名を確認します。
2. `config/config.yaml` の `vision.model` にその名前を設定します。既定は `gemma4-12b-qat` で、`hf.co/google/gemma-4-12B-it-qat-q4_0-gguf:Q4_0` のような完全名も使えます。
3. GUIの設定 → 機能で「Gemma 4 / Ollama」を選択し、必要な場合だけ画像認識またはWebカメラ映像認識をONにします。

ゲーム画面は、最大化・排他フルスクリーンでも安定するOBS Game Captureを推奨します。

1. OBS 28以降を起動し、シーンへ「ゲームキャプチャ」ソースを追加します（録画・配信開始は不要）。
2. OBSの「ツール → WebSocketサーバー設定」でサーバーを有効にします。既定ポートは `4455` です。
3. AItuberの設定 → 機能 → 入力で「OBSゲームキャプチャ」を選び、パスワードを入力します。
4. 「OBS接続・ソース一覧を取得」でゲームキャプチャソースを選び、「選択ソースのフレームをテスト」で現在画面を確認してから適用します。

OBS入力は `GetSourceScreenshot` で要求時点の画像を直接取得します。OBSへ接続できない、ソースが非表示、またはソースが見つからない場合、デスクトップ直接取得へ勝手に切り替えません。

OBSフレームは既定1fpsで直近12秒分をメモリ内に保持します。意味解析は同時に1件だけ実行し、完了後は最新フレームへ追いつきます。会話では画像を毎回12Bモデルへ再送せず、「現在状態・直近の変化・解析済みフレームの経過秒数」をテキストコンテキストとして利用するため、画像付き会話の長いprefill待ちを避けます。

「今どうする？」「危ない、助けて」など現在画面が必要な質問だけは、2秒以内の最新OBS画像を高速リアクティブレーンへ渡します。このレーンは4096コンテキスト・短い出力・思考OFFで、画像からそのまま最終回答を生成します。攻略DBは根拠として渡しますが、本文を固定台詞として直接読み上げません。

```powershell
# Ollamaの接続・モデル確認
ollama list
python -c "from neuro_voice.llm.ollama_multimodal import OllamaMultimodalClient; import asyncio; print(asyncio.run(OllamaMultimodalClient('http://localhost:11434/v1','gemma4-12b-qat').probe(check_image=True)))"
```

Webカメラは初期状態で無効です。`video.enabled: true` と `video.source: 0` を設定して再起動してください。カメラ番号は `0, 1, ...` を順に試します。取得は既定5fps、Gemmaへの解析は差分のある最新フレームを最大4枚・概ね2秒ごとなので、30fpsをそのまま送信しません。

動画ファイルの区間解析はPythonから実行できます。

```powershell
python run.py --analyze-video .\sample.mp4
```

音声認識は `audio_input.backend: whisper` が既定です。`gemma4_audio` は現在のOllama/GGUF経路でネイティブ音声入力を確認できない場合、ログを残してWhisperへ自動フォールバックします。動作したように見せることはありません。

プライバシー上、カメラ映像・Base64画像を会話履歴や通常ログへ保存しません。`privacy.*` で保存方針を確認してください。OllamaやGPUメモリが不足した場合も、映像認識だけを止め、通常の音声会話は継続します。

### 手動確認チェックリスト

1. GUIの「Gemma接続テスト」でOllama接続・モデル存在・画像入力を確認する。
2. テキスト会話を行い、VisionをOFFにして従来の会話が動くことを確認する。
3. VisionをONにし「今何が見える？」と聞き、静止画の構造化観察を会話へ利用できることを確認する。
4. 画面を変えずに続けて話し、同一画面が毎回再解析されないことを確認する。
5. `video.enabled: true` とカメラ番号を設定して再起動し、カメラ使用中ランプと他のアプリが競合しないことを確認する。
6. 手を振るなど場面を変え、「今何してる？」と聞いて最新フレーム列の結果が使われることを確認する。
7. Pythonから `analyze_video_file` を呼び、短いmp4が10秒区間ごとのタイムラインになることを確認する。
8. `audio_input.backend: whisper` でWhisper認識を確認する。
9. `audio_input.backend: gemma4_audio` を選び、未対応環境ではWhisperフォールバック警告が出ることを確認する。
10. `audio_output.backend: voicevox` でVOICEVOX読み上げを確認する。
11. Ollamaを停止し、画像・映像認識だけが失敗してテキスト会話が継続することを確認する。
12. VOICEVOXを停止し、テキスト応答自体は画面へ表示されることを確認する。
13. OBSゲームキャプチャを選び、ゲームを最大化したままプレビューと「今何が見える？」の両方が現在画面になることを確認する。
14. OBSを停止して同じ質問を行い、Web検索や古いデスクトップ画像に切り替わらず、OBS取得エラーが表示されることを確認する。

段階的な動作確認の手順:

1. `config.yaml` の `tts.backend: null` + `python run.py --text` → Cerebras疎通確認
2. `tts.backend: qwen3` + `--text` → TTS確認
3. `python run.py` → フル音声会話

## 設定 (config/config.yaml)

- `llm.backend`: `cerebras` / `openai` / `openrouter` / `ollama` を切替
- `tts.speaker`: `Ono_Anna` (日本語) ほか、`Vivian` `Ryan` など9話者
- `stt.language`: `null`=日英自動判定、`"ja"` 固定で少し高速化
- `stt.beam_size`: 認識候補を同時に比較する数。`1` は最速、既定の `5` は精度と速度のバランス、`8` 以上は精度優先で遅くなる
- `stt.hotwords` / `stt.initial_prompt`: 人名や固有名詞をWhisperへ事前ヒントとして渡す。呼びかけ語の聞き間違いには `stt.wake_word_aliases` を使う
- `vad.end_silence_ms`: 小さくすると応答が早いが、話の途中で切れやすい
- `barge_in.acknowledgement_max_chars`: この長さ以下の既知の相槌を中断扱いしない（既定: 12）
- `aizuchi.after_s` / `aizuchi.min_interval_s`: AI側相槌を始めるまでの長さ / 最短間隔
- `conversation_audio.*`: ダッキング時の音量と、ダッキング・復帰・中断フェード時間
- `user_emotion.*`: openSMILEの音響特徴量とSpeechBrainの確率付き感情推定。初回のみモデルを取得
- `style_manager.user_emotion_confidence_threshold`: 高確信のユーザー感情を声の数値調整へ反映する境界値
- `search.max_queries`: LLMが曖昧さを解消して作成する検索語の上限。検索後は別のLLM処理で質問に必要な根拠だけを抽出する
- `persona.system_prompt`: 人格の定義
- `persona.presets.<name>.voicevox_speaker`: そのペルソナで最後に選んだVOICEVOX話者。ペルソナ切替時に自動で復元

## こころ (Mind): 記憶と成長する人格

`mind.enabled: true` (既定) で、キャラクターが会話を覚え、少しずつ成長する。

**3層の記憶**

| 層 | 実体 | 寿命 |
|---|---|---|
| 短期 | 会話履歴そのもの (`conversation.max_turns` 往復) | セッション中 |
| 中期 | LLMが数ターンごとに更新するセッション要約 | セッション中 (終了時に思い出化) |
| 長期 | SQLite + ローカルembedding意味検索 (事実・好み・思い出) | 永続 |

**成長する人格**

- 性格6パラメータ (明るさ・好奇心・思いやり・いたずら心・自信・素直さ) が
  会話の内容で少しずつ変化する (1回の内省で最大±0.03)
- 気分 (valence/arousal) は会話の感情で動き、時間と共に性格由来の基準へ戻る
- 好み (すき・きらい) が会話の中で芽生えたり変わったりする
- 親密度: 会話量と日数でレベルが上がり、距離感・口調が変わる
  (はじめまして → 顔見知り → 話し相手 → 友達 → 親友 → 相棒)

仕組み: 数ターンごとに会話の合間を見てLLMが1回だけ「内省」し、
記憶の抽出・要約更新・人格の微小変化をまとめて行う (応答速度に影響しない)。
毎ターン、人格状態 + 要約 + 想起した記憶が system prompt に注入される。

- GUI右上の **💠 ボタン**でステータス画面 (性格・気分・すききらい・なかよし度・記憶) を確認できる
- 記憶と人格は**ペルソナごとに別ファイル**で育つ (`data/`)
- `mind.growth_rate` で成長速度を調整 (0で成長停止)
- sentence-transformers 未導入でも動く (キーワード検索にフォールバック)
- 会話の個性・創造性・関係性・自己成長と開発者向け観測項目は
  [会話エンジン v4](docs/conversation_engine_v4.md) を参照

**話者識別 (声で相手を覚える)**

`speaker.enabled: true` (既定) で、声紋 (WavLM x-vector の ONNX 版・CPUで数百ms) により
「誰が話しているか」を識別する。知らない声は「ゲストn」として自動登録され、
会話の流れで名乗ってもらうと名前を学習する (「俺は〇〇」→ 以後その名前で呼ぶ)。
記憶も「(名前)は〜」の形で人に紐づいて保存される。
チャットのユーザー吹き出しに話者名が表示され、💠画面の「はなし相手」から
名前の変更・削除ができる。声紋データ・話し相手ごとのなかよし度は
`data/speakers_<persona>.json` としてペルソナごとに独立して保存される。

**ユーザー音声の感情認識**

`user_emotion.enabled: true` (既定) で、openSMILEがeGeMAPS音響特徴量を抽出し、
SpeechBrainが感情を確率付きで推定する。結果はテキストとともにLLMへ渡され、
`style_manager.user_emotion_confidence_threshold` 以上の確信度だけがAI側の話速・抑揚へごく小さく反映される。

## Discord連携 (グループ通話に参加)

ボイスチャンネルに参加し、**全員の声を聞き分けて名前を呼びながら会話**する。

### グループ通話とプライバシー

グループ通話では、名前を呼ばれなくてもAIへの追質問や全体質問へ参加できる一方、曖昧な質問では短時間人間の回答を待つ。人間が話し始めた場合は待機中のAI応答を取り消す。

通話で発言された内容は、その時点で参加者には聞こえている。AIが防ぐのは、別の通話・別の参加者構成での持ち出し、またはAIからの不要な再発話である。パスワード・トークン・連絡先などは保存・復唱しない。過去の一対一記憶や出所不明の記憶は、グループ用LLMコンテキストへ渡さない。
Discordはユーザーごとに音声が分離されているため、話者の特定は確実。
記憶・人格 (Mind) も共有されるので、通話で聞いた話をローカル会話でも覚えている。

```powershell
pip install "discord.py[voice]" discord-ext-voice-recv
python run.py --discord
```

セットアップ:
1. https://discord.com/developers/applications で Bot 作成 → MESSAGE CONTENT INTENT を ON
2. トークンを `.env` の `DISCORD_BOT_TOKEN` に設定
3. OAuth2 URL Generator (scope: bot / 権限: View Channels, Send Messages, Connect, Speak) でサーバーへ招待
4. VCに入ってからテキストチャンネルで `!join`、退出は `!leave`

`discord.respond_all: false` にすると、名前 (wake_words) を呼ばれた時と
自分が話した直後だけ応答する (大人数の通話向け)。

## 自律行動（イベント駆動）

`autonomous_action_system.enabled: true` では、ポッポは沈黙を埋めるためにランダムな話題を作りません。人の発話、ゲーム上の変化、ツール結果、期限を迎えた保留話題だけをイベントとして評価し、`ANSWER`、`COMMENT`、`REPORT_RESULT`、`WAIT`、`UPDATE_MEMORY`、`DO_NOTHING` から選びます。

- `DO_NOTHING` は失敗ではありません。短い相づち・独り言・人間同士の会話では、会話状態だけを更新して黙ります。
- 保留話題は `OpenThread` として短時間保持し、自然な沈黙で最大2回まで回収候補になります。プライベートな話題はグループで回収しません。
- 自律発話は通常のTTS・割り込み・キャンセル経路を使います。人が話し始めると未完了の自律発話はキャンセルされます。
- 旧来のタイマー／ランダム型は `legacy_spontaneous_mode.enabled` です。自律行動と同時には有効化されません。

## 文脈長と「応答が途中で切れる」

文脈長は「送る分」と「返す分」で**共有**されます。会話履歴を往復数（`conversation.max_turns`）だけで打ち切ると、ターンごとの長さの違いを無視することになります。TRPG のように1ターンが長い会話では、数往復で `num_ctx` が埋まり、出力に残る枠が数十トークンしかなくなります。すると応答は数文字で `finish_reason=length` に達し、**文の途中で切れます**。

送信前にトークン量を見積もり、`llm.context_reserve_tokens` の分だけ出力枠を必ず空けてから、古い往復を落とします。system メッセージ（人格・今回の判断・検索の根拠）は落としません——静かに落とすと**答えている人格そのものが変わる**からです。

### num_ctx と max_tokens の関係

```
num_ctx 8192  ┌────────── プロンプト ──────────┬── 出力 ──┐
              │ 人格 + 記憶 + 履歴 + 今回の発話 │          │
              └────────────────────────────────┴──────────┘
                                    max_tokens はこの右側だけの上限
```

実際の出力上限は `min(max_tokens, num_ctx − プロンプト)` です。`num_ctx` を上げて増えるのは**履歴に使える枠**であって、応答の長さではありません。音声会話なら `max_tokens: 1024`（日本語で約1000字＝2分半の発話）で十分です。

連動が必要なのは `context_reserve_tokens` のほうです。既定の `auto` は `max_tokens + 余裕` を自動で導出するので、`max_tokens` を変えても予約が追従します。**固定値にしないでください**——上げ忘れると応答がまた文の途中で切れ、しかも設定の問題には見えません。小さすぎる固定値を書いた場合は警告して自動値へ引き上げます。

既定は `num_ctx: 8192` / 予約 `auto`（＝1280）で、履歴に使えるのは約6900トークン（日本語で約6500字）です。

**`num_ctx` はサーバ側と必ず揃えてください。** config だけ上げてもサーバの上限で頭打ちになります。

```
config/config.yaml     llm.num_ctx: 8192
SetupOllamaEnv.bat     setx OLLAMA_CONTEXT_LENGTH 8192   ← 実行し直すこと
```

VRAM は KVキャッシュぶん増えます。`OLLAMA_KV_CACHE_TYPE=q8_0` が効いているので 4096→8192 でおおよそ +0.2〜0.8 GB（モデルの注意機構によって幅があります）。実測は `ollama ps` の SIZE で確認できます。

### 毎回同じ昔話をしてくる

自発発話の「話題」は、実は**発話まるごと**が保存されていました。日本語は分かち書きしないので、漢字・ひらがな・カタカナを1つの文字クラスで拾うと**文全体が1語**になります（STTの語彙抽出と同じ種類の不具合です）。

```
'今あのマイクオンにしたまま声口元から話してたわ'
   → ['今あのマイクオンにしたまま声口元から話してたわ']   ← これが「話題」として永続化
```

これが毎起動時の自発発話の種になり、同じ話を延々と繰り返していました。字種で切り分けるよう直し、**既に保存されている壊れた値は読込時に掃除**します（長さでは「特に何もないんだけど」を弾けないので、現在の抽出器が生成しうる形だけを残します）。

あわせて、**このセッションでユーザーが一度も話していない間は「今の話題」を持たない**ようにしました。起動直後に前回の残りかすを現在の話題として扱うのは、そもそも間違いです。

### 別の物語が混ざってくる

区間の材料として渡していた「直近の記憶」に見出しが無く、モデルはそれを**今話すべきこと**として読んでいました。前のラジオで作った架空設定が、進行中の TRPG に流れ込んで話題ごと入れ替わる事故が起きています。

- 物語モード（`NARRATION`）では記憶も興味も**一切渡しません**。物語は自己完結すべきものです
- 他モードでは「別の場面で覚えたこと（今の話題と関係する時だけ使う。関係なければ完全に無視する）」と明示します
- 会話の途中で継続依頼が作られた場合、**今の主題を引き継ぎます**。「一緒にやろう」が進行中の物語を捨てて無関係な相談を始めないようにするためです

## あとから接続したマイク・スピーカー

ヘッドセットの電源を切ったまま起動して、あとから入れても認識しない——という状態でした。原因は3つあります。

- **PortAudio はデバイス一覧を起動時にキャッシュする。** あとから現れた機器はそもそも見えません。一覧を取り直す必要があります
- **マイクは開けなかった時点で諦めていた。** 例外がそのまま上がるので、以後の復帰手段がありませんでした
- **再生スレッドはストリーム生成に失敗すると死んでいた。** ループ全体が1つの `try` に包まれており、一度落ちたスレッドは二度と戻りません

`audio.device_watch_interval_s`（既定3秒）ごとにデバイス一覧を取り直し、既定デバイスの変化かマイクの停止を検出したら開き直します。発話中・応答中には切り替えません（ターンを途中で切らないため）。Discord がマイクを持っている間も勝手に開き直しません。

マイクが無い状態で起動しても**アプリは動き続け**、接続した時点で「🎤 マイクを認識しました」と表示されます。`0` にすると監視を止めて従来どおり起動時のデバイスに固定できます。

## 起動時間

音声合成・音声認識・こころ（声紋）は互いに依存しません。にもかかわらず順番に読み込んでいたため、起動時間が**それぞれの合計**になっていました。

```
before  SBV2起動(19s) → faster-whisper(24s) → 声紋(2s)  = 約51秒
after   3つを並行し、最も遅いものだけ待つ                = 約28秒
```

依存パッケージの確認も見直しました。`find_spec("discord.ext.voice_recv")` は親パッケージを**実際に import** するため、`discord` の読み込み数秒がウィンドウ表示前に乗っていました。インストール済みディストリビューションのメタデータから判定するようにして、import 自体をなくしています。

さらに短縮したい場合の候補（未実装）: TTS の準備完了を待たずにマイクを開ける。最初の返答までには数秒あるので原理的には可能ですが、パイプライン構築の順序を変える必要があります。

## 音声認識の誤変換対策（同音異義語）

日本語の音声認識は特徴的な壊れ方をします。**音は合っていて漢字が違う**——「マイクラ」が「毎クラ」、「お水」が「小水」。書き起こしを確定した事実として扱うと、AIは実在しない語を真面目に解釈して、意味の通らない返答をします。

認識結果は「確定した文字」ではなく**仮説**として扱い、安い順に3段構えで対処します。

1. **デコード時バイアス**（`ContextVocabulary`）— 名前・現在のゲーム名など**検証済みの固有名詞だけ**を `hotwords` へ渡し、Whisperの認識自体を寄せる
2. **読み一致の自動修正** — 語ごとの確信度が低く、かつ**読みが文脈語と完全一致**する語だけ黙って置換（「まいくら」→「マイクラ」）。読みが同じ文脈語が複数ある時は**推測せず候補として残す**。誤りを別の誤りに移し替えないため
3. **不確実性の伝達** — 残った怪しい語をLLMへ渡し、「漢字の意味で解釈せず、同じ読みの別語として文脈から読み替えよ」と指示する

**追加のLLM呼び出しはありません。** 応答遅延は増えません（word-level 確信度の取得分だけ認識がわずかに遅くなります）。

振る舞いの方針は「基本は推測して進む」です。読み替えれば意味が通るなら止まらずに答え、**変換ミスの話題自体には触れません**（「音声認識が」のようなメタ発言をしない）。どう読み替えても意図が取れない時だけ、一言で短く聞き返します。

`stt.transcript_repair.enabled: false` で従来動作へ戻ります。漢字語の自動補正には読み変換バックエンド（`pykakasi` か `pyopenjtalk`）が必要で、無い環境ではカタカナ・ひらがな間の補正だけが有効になります。

### 話し始めの「えーと」「うん」を落とさない

人は整った文から話し始めません。「えーと」「うん」「あのー」で口を開き、VAD が確信を持つのはその**次の語**です。ここが2箇所で落ちていました。

**1. VAD が語頭を無音として捨てていた。** pre-roll のうち「トリガー直前の `keep_leading_ms` 以外はすべて無音」と決め打ちしていました。実際にはフィラーがそこに入っています。フレームごとの確率を保持し、`onset_threshold`（開始しきい値より低い 0.20）で**本当に無音な先頭だけ**を削るようにしました。pre-roll も 320ms → 640ms へ広げています。

**2. Whisper が整形して落としていた。** Whisper は綺麗な字幕を作るよう学習されており、`initial_prompt` の文体を真似ます。整った例文だけを与えると言いよどみを消します。既定プロンプトにフィラーを含め、`suppress_tokens` の既定抑制も外しました（`stt.keep_fillers`）。

`keep_fillers: false` で従来の綺麗な書き起こしに戻せます。

### バイアスは「認識を助ける」より簡単に「認識を壊す」

ここは一度失敗しています。会話履歴から拾った語を `initial_prompt` と `hotwords` へ大量に流し込んだところ、Whisper が**そのバイアス語を出力へ挿入**しはじめました（「さあ、ib ポッポ、ポッポ、チビをカリメと言うと」）。さらに悪いことに、前回の誤認識がそのままバイアス語になり、**誤りが自分を強化するループ**ができていました。

そのため語彙は2つに分けてあります。

| | 中身 | 認識への影響 |
|---|---|---|
| `bias_terms` | 名前・現在のゲーム名（検証済み・最大8語） | **あり**（hotwords） |
| `repair_terms` | 会話の話題・記憶・興味（広め） | **なし**（読み一致の後処理だけ） |

書き起こし由来の語は決してデコーダへ渡しません。間違っていても後処理で候補を出すだけなのでコストがゼロだからです。`initial_prompt` への語彙注入は既定でオフです（Whisper はプロンプト文をそのまま喋り返すことがあります）。`bias_via_initial_prompt: true` で有効化できますが推奨しません。

同じ理由で `repetition_penalty` も既定 1.0（無効）です。日本語は正当な反復が多く、ペナルティを掛けると反復を避けるために**別の語へ置換**してしまいます。

### 復号ループ（吃音）の抑制

「最初は、最初は、最初は、」「仕事ではよく使って、仕事ではよく使ってるし」——Whisper が同じ句を繰り返す既知の壊れ方です。`temperature` を 0.0 に固定すると Whisper 自身の再試行フォールバックが無効になるため、温度ラダーと反復ペナルティを既定で有効にしています。それでも残った隣接反復は書き起こし後に畳みます。長い句は2回で、短い句は3回以上でループとみなすので、「そうそう」「はいはい」は残ります。

## 検索するのか、何をしていたか聞かれているのか

「調べて」は依頼にも過去形の質問にも現れます。単純な部分一致で判定すると、**「何調べてたの?」**（直前の発言についての質問）が検索命令になり、無関係なページが根拠として返り、AIがそれを**自分がやったこと**として報告します。一度の部分一致が偽の記憶を作ります。

判定は `search/intent.py` に一本化してあり、Conversation Kernel と検索プランナの両方がこれを使います（二重定義は必ずズレるため）。加えて、検索根拠を注入するメッセージには出所の境界を明示し、「今Webから取ってきた外部情報であり、自分の過去の行動ではない」ことを必ず伝えます。

## 同一人物の統合（1人、複数の場面）

同じ人がローカルマイクでは「チビ」、Discord のニックネームでは「ジーレン」——これで**声紋プロファイルが2つ**できます。見た目の問題ではありません。なかよし度・会話プロファイル・学習した好みはすべて `speaker:{id}` をキーに保存されているため、ポッポはその人を**半分ずつの履歴を持つ別々の2人**として知ることになります。

「こころ」ステータスの「はなし相手」から統合できます。

- 各行の 🔗 ボタン、または声紋が近い組み合わせの自動提案から実行
- 声紋の重心はサンプル数で加重して合成するため、育ったプロファイルが新しい方に引っ張られません
- 会話回数は合算、出会った日は古い方、信頼・親密度は高い方を採用
- 摩擦系の指標（警戒・苛立ち・緊張・疲労）は**低い方**を採用します。1人になったからといって両方分の摩擦を背負う理由はありません
- 関係性・会話プロファイル・適応学習の記録もすべて移行します

**自動統合はしません。** 兄弟が同じマイクを使えば声紋は近くなるので、提案までに留めて実行は必ず人が選びます。

呼び名は場面別に保たれます（`aliases`）。ローカルでは「チビ」、Discord では「ジーレン」と呼びかけつつ、中身は1人のままです。Discord のニックネームは発話のたびに自動で別名として記録されるので、次に統合したときも両方の名前が残ります。

## 話者識別のヒステリシス

声紋のコサインスコアはターンごとに数%揺れます。素の最良一致で決めると、同じ人の連続発話が「ジーレン→チビ→ジーレン」と入れ替わり、別人が話しているように見えます。直近 `speaker.sticky_window_s` 秒以内に話した人を継続中の話者とみなし、他人が `speaker.sticky_margin` 以上明確に上回った時だけ切り替えます。明らかに別人の声、および除外指定された話者には適用されません。

## 継続行動（BehaviorDirective）

「しばらくラジオみたいに話して」「ゲームが終わるまで実況して」「一緒に考えて」「静かに見守って」——こうした依頼は、1回の返答では終わりません。`behavior_directive.enabled: true` では、これらを**専用エンジンではなく共通の継続依頼（BehaviorDirective）**として保持します。ラジオ専用・実況専用のクラスは存在しません。

```
ユーザーの依頼 → Conversation Kernel（単発か継続かを判断）
              → Intent-to-Plan（LLMが目的と進め方を解釈）
              → BehaviorDirective として保持
              → ContinuationController が区間ごとに実行
              → 各区間でLLM自身が次の行動を決める
```

- **LLMが決めるもの**: 何を話すか、どの話題を選ぶか、いつ黙るか、いつ自然に終わるか。
- **コードが決めるもの**: 時計、区間の順序、state version、発話権、ツール権限、上限、停止。
- **ExecutionMode**: `ONE_SHOT_RESPONSE` / `STREAMED_LONG_RESPONSE`（ラジオ）/ `ONGOING_DIRECTIVE`（実況）/ `COLLABORATIVE_SESSION`（共同思考）/ `OBSERVATION_DIRECTIVE`（見守り）。
- **各区間の行動**: `SPEAK` / `ASK_USER` / `USE_TOOL` / `COMMENT_ON_EVENT` / `WAIT` / `CHANGE_TOPIC` / `REVISE_PLAN` / `FINISH`。実況・見守りでは `WAIT`（黙る）が正常な結果です。イベントがなければ喋りません。
- **割り込み**: 人が話し始めると再生中TTSを止め、未再生を破棄し、生成中の区間を破棄します。依頼は**キャンセルではなくPAUSE**され、新しい発話に答えた後で再開・修正・終了を判断します。
- **修正**: 継続中の「もっとゲームの話を中心に」「質問はしないで」は、新しい依頼ではなく既存依頼の修正として扱われ、`state_version` が上がって古い出力は破棄されます。
- **背圧**: `tts_max_queued_segments` / `tts_max_ahead_seconds` により、再生より大きく先行して合成しません。
- **ループ検出**: 言い回しが違っても同じ導入・同じ話題・同じ質問の繰り返しを検出し、話題転換か終了へ進みます。
- **上限**: `max_duration_seconds`（既定30分）、`max_segments`、`max_consecutive_errors`。再起動時、短い依頼は復元せず `CANCELLED_BY_RESTART` として履歴に残します。
- **権限**: 依頼は自分でツール権限を広げられません。`allowed_tools` はホワイトリストで検証され、検索は既存の SearchDecision / PrivacyManager を必ず通ります。

### 頼まれた形が、既定より強い

この基盤には速度と一貫性のために**固定の雛形**と**固定のモード指示**があります。どちらも近道であって規則ではありません。近道が依頼を黙って上書きするのは、頼んだ人の話を聞いていないのと同じです。

```
「GM兼プレイヤーとしても参加して」
```

に対して「あなたは物語の外にいる。自分用のキャラクターを作らない」と答えるのは矛盾です。そうならないよう3層にしてあります。

1. **雛形は素の依頼だけを扱う。** 「兼」「〜としても」「私も参加」「両方」のような条件や、複数の形に当てはまる依頼（「実況しながら一緒に考えて」）は雛形が引き下がり、LLM が解釈します
2. **モード指示は「既定」として提示する。** 依頼本文や `style_constraints` と食い違う場合は依頼が優先されると明示しています
3. **依頼の原文がプロンプトに載る。** 雛形を使った場合でも、モデルは本人の言葉をそのまま見ます

`NARRATION` で依頼によらず守るのは**一点だけ**です——相手のキャラクターの行動を勝手に決めない。それ以外（GMが自分のキャラで参加するかどうかも含めて）は頼まれた形に従います。会話の途中で「やっぱりきみも参加して」と言えば、修正として反映されます。

**ターン制の依頼（`needs_user_input`）では、通常の返答こそが進行役の手番です。** 返答のあとに区間を生成すると、同じ場面を描写して同じ問いを二度することになります。返答を手番として記録し、相手が答えるまで `WAITING_FOR_USER` で待ちます。ラジオのような一人語りはこの規則の対象外で、従来どおり自分から区間を出し続けます。

継続依頼中は、**通常の返答にもモード指示が渡ります**。ここが抜けていたため、進行役が自分は進行役だと知らないまま自分のキャラクターを作り、物語の中で行動してしまっていました。

TRPG・なりきり・物語進行は `NARRATION` モードの継続依頼になります。**相手のキャラクターの行動を決めない**ことがこのモードの本質なので、描写を終えたら必ず相手の番を渡して待ちます。継続依頼が走っている間は自律発話が抑止されるため、進行中に横から話しかけて場を壊すこともありません。

**次の区間は、今の区間を再生している間に書きます。** 再生が終わってから生成を始めると、区間の切れ目ごとにモデル1往復ぶんの無音が入ります。「発話権が塞がっている」の判定には**自分の再生を含めません**——含めると先読みが一度も発動しません。どこまで先走ってよいかは `tts_max_ahead_seconds`（既定15秒）が決めます。人が話し始めた時だけ生成を止めます。

一人語りが短く終わらないよう、時間指定のない依頼には `default_duration_seconds`（既定5分）を与えます。目標がないとモデルは2〜3区間で自然に締めてしまいます。また `min_duration_seconds` に満たないうちの FINISH は「締め」ではなく手詰まりとみなし、話題転換を促して続けます（`max_early_finishes` 回まで。無限に押し問答はしません）。イベント駆動の依頼（「ゲームが終わるまで」）は時計で終わるものではないので、この制限は適用されません。

区間は**文単位で合成**されます。段落をまとめて1リクエストにすると、本文をクエリ文字列に載せる TTS バックエンド（Style-Bert-VITS2）で URL 長超過になり、しかも段落を読み終えるまで割り込めません。

依頼の解釈（Intent-to-Plan）は**最初の返答と並行**して走ります。返答の前に待つと、モデル1往復ぶんの遅延がそのまま「話しかけてから最初の一言まで」に乗ります。返答後 `plan_settle_timeout_s` だけ待ち、間に合えばその返答を1区間目として引き継ぎます。

**ローカル音声とDiscordは同じ基盤を共有します。** 判断（Kernel＋ContinuationController）は Mind が一元管理し、区間の実行は `DirectiveRuntime` という共通ランタイムが担います。各サーフェスが提供するのは「どう喋るか」「発話権が空いているか」「どれだけ音声が溜まっているか」「どのツールが使えるか」だけです。Discord では VC に人が一人もいない間は喋らず、VC 退出で依頼は終了します。

状態は「こころ」ステータスの「継続中の依頼」カードで観測できます。`behavior_directive.enabled: false` で従来の単発応答へ戻ります。

## 自律研究（低優先度・安全境界付き）

`autonomous_research` は、通常の即時Web検索とは別に、具体的な疑問や「あとで調べておいて」という依頼を会話後に調べるキューです。Heartbeatはキューの保守だけを行い、沈黙から検索話題を作りません。個人情報・資格情報・医療・法律・金融・政治・セキュリティは自動検索しません。検索結果は出典と検証状態をペルソナ別SQLiteへ保存し、単一ソースは暫定情報として扱います。詳細は [自律研究の仕様](docs/autonomous_research.md) を参照してください。

主な調整値は `autonomy.min_speech_utility`、`autonomy.silence_evaluation_min_ms`、`autonomy.open_thread_default_ttl_minutes`、`autonomy.group_speech_threshold_bonus` です。

## 時間的自己認識・連続感情・音声抑揚

`temporal_self.enabled: true` では、ペルソナごとに稼働セッション、heartbeat、利用間隔、復帰時の文脈、集計済みの感情状態だけを保存します。会話本文や音声をこのデータへ複製しません。日付・不在期間はUTC基準で保存し、表示と会話は `temporal_self.timezone`（既定 `Asia/Tokyo`）で行います。

`affect.enabled` は感情をイベントごとに小さく更新し、離席中には徐々に減衰させます。`voice_affect.enabled` は既存のStyleManagerの出力を滑らかにし、VOICEVOX / Style-Bert-VITS2 の両方で速度・ピッチ・抑揚・音量が一発話ごとに急変しないようにします。調整値は `voice_affect.attack_rate`、`voice_affect.release_rate`、`voice_affect.max_delta_per_utterance` です。モデルに該当するSBV2スタイルがない場合は、従来どおりニュートラルスタイルへ安全にフォールバックします。

## トラブルシューティング

- **faster-whisper で cuDNN エラー**: cuDNN 9 (CUDA 12用) のDLLが必要。
  `pip install nvidia-cudnn-cu12` 後、そのDLLフォルダをPATHに追加するか、
  NVIDIA公式からcuDNNを入れる。動かない場合は `stt.compute_type: int8` も試す。
- **エコーで barge-in が誤発動**: ヘッドホン推奨。まずは `vad.start_frames_barge_in` を増やす。
  それでも改善しない場合は `barge_in.enabled: false` にすると、AI発話中の入力を中断として処理しない。
- **Qwen3-TTS が遅い**: `flash-attn` を導入して `tts.attn: flash_attention_2`。
  それでも遅い場合はまず 0.6B モデルであることを確認。
- **Cerebras 429エラー**: 無料枠は30リクエスト/分。連続で話しすぎると制限される。
